# Invariants System Design

## Purpose

An invariant is a falsifiable statement about what the system does or guarantees, independent of how it's implemented. Invariants allow verification that documentation and code agree, surface implementation gaps, and serve as a living test plan.

The system extracts invariants independently from documentation and code, then compares them. The independence is the point — if both sources agree, that's a strong signal. If only one mentions something, that's a gap worth investigating.

## What Makes a Good Invariant

**An invariant is a falsifiable statement about the system that can be checked against the implementation.**

Properties of good invariants:

- **Falsifiable** — you can look at the code and say "this is true" or "this is false". Not vague ("the system is fast") but specific ("file watcher debounces at 2 seconds before emitting SSE events").
- **Atomic** — one claim per invariant. If it contains "and", it's probably two invariants.
- **Stable** — describes intended behaviour or deliberate architectural choice, not incidental implementation detail. "Plans require human approval" is stable. "Line 47 of planner.ts calls `await confirm()`" is fragile.
- **Hierarchical** — parent invariants are broader ("agents operate reactively"), children are specific ("the watcher triggers on filesystem events, not on a polling interval").
- **Sourced** — traces back to a specific wiki page or code location.
- **Verification-aware** — each invariant has a natural verification method (unit test, integration test, visual QA, static analysis, manual check).

Bad invariants:

- Tautologies ("the system does what it does")
- Implementation details disguised as requirements ("uses a Map<string, Page> for storage") — unless the implementation choice is a deliberate architectural decision
- Unmeasurable qualities ("the UI is intuitive")

## Two Kinds of Invariant

**Behavioural invariants** — what the system does, language-agnostic. These survive a rewrite in a different language. "A user can chat with a page and the page updates in response." Verified by running the system (integration tests, visual QA).

**Architectural invariants** — how the system is structured, deliberately chosen and load-bearing. "The system runs as a single Bun process." "Pages are stored as flat markdown files." These are decisions that constrain the design space — they *would* change in a rewrite, and that's the point. Verified by static analysis of codebase structure (imports, dependencies, file layout).

The distinction maps to the wiki taxonomy: architectural invariants typically come from `architecture` and `decisions` pages, behavioural ones from `functionality`, `pipeline`, `ui`, etc.

## Verification Methods

Each invariant specifies how it should be verified:

| Verification type | Example | Automation |
|---|---|---|
| Unit test | "Frontmatter parsing extracts all required fields" | Bun test |
| Integration test | "Saving a page via the API makes it appear in search results" | Bun test with server |
| Visual QA | "The sidebar shows pages grouped by category" | Screenshot comparison or manual |
| Manual check | "The wiki-first workflow is documented in CLAUDE.md" | Human review |
| Static analysis | "Every wiki page has exactly one category" | Script or grep |

The invariant tree is also a test plan — each leaf says *what* should be true and *how* you'd verify it.

## Data Model

### Directory structure

```
wiki/invariants/
  tree.json              # the full spec-derived invariant tree
  evidence.json          # code-side evidence mapped to invariant IDs
  report.json            # comparison output (gaps, coverage)
  agent-pipeline.md      # rendered wiki page per top-level group
  batch-import.md
  ...
```

### Invariant node

```json
{
  "id": "agent-pipeline.watcher.debounce-timing",
  "parent": "agent-pipeline.watcher",
  "description": "The file watcher debounces filesystem events for 2 seconds before emitting SSE updates",
  "kind": "behavioural",
  "verificationMethod": "integration-test",
  "sources": ["file-watcher-debounce"]
}
```

- `id` — dotted path encoding the hierarchy. The top-level segment (before the first dot) is the **group name** and determines which invariant wiki page the invariant appears on. IDs are generated by the Sonnet agent and may vary between runs; the comparison stage matches on description similarity, not ID equality.
- `kind` — `behavioural` or `architectural`.
- `sources` — wiki page slugs where the invariant was derived from (array, since multiple pages may describe the same invariant).

### Evidence entry

```json
{
  "invariantId": "agent-pipeline.watcher.debounce-timing",
  "implemented": true,
  "tested": true,
  "codeLocations": ["src/watcher/debounce.ts"],
  "testLocations": ["src/watcher/__tests__/debounce.test.ts"]
}
```

### Unspecified invariant entry

Invariants discovered in code but not in the spec tree are stored separately in `evidence.json`:

```json
{
  "description": "The server returns 404 with a JSON error body for unknown page slugs",
  "codeLocations": ["src/server/routes/pages.ts"],
  "testLocations": ["src/server/__tests__/pages.test.ts"]
}
```

These have no `invariantId` (they aren't in the spec tree). They appear in the gap report for human review.

### Status values

After comparison, each invariant gets a status:

- **implemented-tested** — code evidence exists, test covers it
- **implemented-untested** — code evidence exists, no test
- **specified-only** — wiki says it, no code evidence found
- **unspecified** — found in code/tests but not in wiki

Coverage is the percentage of spec invariants with status `implemented-tested` or `implemented-untested` (i.e. have code evidence, regardless of test coverage).

## Three-Stage Pipeline

### Stage 1: Spec extraction (Sonnet subagents)

For each wiki page, a Sonnet subagent reads the page content and extracts invariants. It never sees source code. The prompt asks for falsifiable, atomic statements organised hierarchically, tagged as `behavioural` or `architectural`, with a suggested verification method.

Pages are batched by category so the agent has enough context to avoid duplicates within related pages (e.g. `batch-import-pipeline` and `batch-import-map-reduce` might both mention the confidence threshold — it should appear once).

After all category batches complete, a **deduplication pass** merges invariants with substantially similar descriptions across categories. This is a Sonnet call that reads all extracted invariants and merges duplicates, combining their `sources` arrays. The result is a single deduplicated tree. At larger scale (hundreds of invariants), this pass may need batching — but at current project size it fits comfortably in a single prompt.

Output: `wiki/invariants/tree.json`

### Stage 2: Evidence extraction (Sonnet subagents)

For each top-level invariant group, a Sonnet subagent receives the invariant descriptions (from `tree.json`) and the relevant source files + test files. It never sees wiki pages. Its job is to find evidence:

- Does code exist that implements this invariant?
- Does a test exist that verifies it?
- Are there things in the code that aren't covered by any invariant?

**File scoping:** The evidence agent needs to know which source files to examine. The approach:

1. The invariant group name maps to `src/` subdirectories by convention (e.g. group `batch-import` → `src/batch-import/`). A mapping table in the skill config handles non-obvious mappings (e.g. group `agent-pipeline` → `src/watcher/`, `src/agents/`).
2. For each group, the coordinator also runs a grep for key terms from the invariant descriptions across the full `src/` tree, adding any matched files to the set. This catches invariants implemented in unexpected locations.
3. Test files are included by looking for `__tests__/` directories adjacent to matched source files, plus any top-level test files matching the group name.

This keeps the evidence agent's context focused without requiring it to read the entire codebase.

**Unspecified invariants:** When the evidence agent finds code behaviour not covered by any spec invariant, it records these in a separate `unspecified` list. These are surfaced in the gap report for human review. They are not automatically added to `tree.json` — a human decides whether to add them to the wiki (which will cause them to appear in the spec tree on the next run) or to ignore them. This keeps the spec tree as a deliberate document of intent, not an auto-generated mirror of the code.

Output: `wiki/invariants/evidence.json` — maps invariant IDs to source locations and test locations, plus a list of unspecified invariants discovered in code.

### Stage 3: Comparison (single Sonnet agent)

Reads `tree.json` and `evidence.json` only. Produces:

- Status for each invariant
- A gap report: what's specified but missing, what's implemented but undocumented
- Rendered markdown files for `wiki/invariants/`

Output: `wiki/invariants/report.json` + `wiki/invariants/*.md`

### Context isolation

Each stage sees only its own inputs. The spec agent never sees code. The code agent never sees wiki pages. The comparison agent sees only the structured JSON outputs. This prevents one source from biasing the other.

## Invariant Wiki Pages

Each top-level invariant group gets a wiki page in `wiki/invariants/`. Example:

```markdown
---
title: Agent Pipeline Invariants
group: agent-pipeline
generated: 2026-03-14
coverage: 72%
---

## The system uses a reactive agent pipeline

**Kind:** architectural | **Status:** implemented-tested
**Verification:** static-analysis | **Source:** [[system-architecture]]
**Evidence:** `src/index.ts`, `src/watcher/index.ts`

### File changes trigger a watcher agent

**Kind:** behavioural | **Status:** implemented-tested
**Verification:** integration-test
**Evidence:** `src/watcher/index.ts`, `src/watcher/__tests__/watcher.test.ts`

#### The watcher uses Haiku
...

## Gaps

| Invariant | Status | Notes |
|---|---|---|
| Plans require human approval | specified-only | No approval gate in code |
| Execution happens on git branches | specified-only | Branch creation not implemented |
```

The `coverage` field in frontmatter gives a quick signal — the percentage of spec invariants in this group that have status `implemented-tested` or `implemented-untested` (i.e. have code evidence, regardless of test coverage).

Regular wiki pages can reference invariants: "The debounce timing is a system invariant — see [[inv:agent-pipeline]]."

## Skill Interface

```
/octowiki:invariants [--stage 1|2|3] [--group <group-name>]
```

- Default: runs all three stages
- `--stage N`: re-run just one stage (e.g. re-run evidence extraction after writing new tests)
- `--group <name>`: scope to a single invariant group

Results are written directly to `wiki/invariants/` — no staging step needed since these are generated artifacts, not hand-written content.

## Incremental Runs

Full pipeline runs re-extract everything. This is acceptable at current scale (38 wiki pages, ~40 source files) but would become wasteful as the project grows.

The `--stage` and `--group` flags support partial re-runs today. A future optimisation could use git diff to detect which wiki pages or source files have changed since the last run and scope extraction accordingly. The `tree.json` and `evidence.json` files would be merged rather than replaced. This is not needed for v1.

## Error Handling

If a Sonnet subagent fails during Stage 1 or 2, the successful results are preserved. The failed batch/group is recorded in `report.json` as an error. The `--stage` and `--group` flags allow re-running just the failed portion without repeating successful work.

## Future: Invariant Extraction at Page Creation Time

Out of scope for this design, but the architecture supports it. The batch-import reduce step and the add-page skill could both emit invariants alongside the wiki page content. This would capture intent from the original source material at the point of documentation, before any synthesis drift. The `tree.json` structure is the same — it just gets populated earlier in the pipeline.

## Linking

Invariant pages live in `wiki/invariants/`, separate from `wiki/pages/`. They use a `[[inv:group-name]]` wikilink syntax to be referenced from regular pages. This keeps the hand-written/imported documentation structurally separate from the generated verification artifacts, while allowing cross-references between them.
